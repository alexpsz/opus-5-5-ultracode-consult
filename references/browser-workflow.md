# Connected browser consultation

Use this route for interactive work in the signed-in official client connected to the intended machine/project. CLI remains useful for programmatic background processes, exact parameters and automatic raw-stream collection. Both routes can write authorized local outputs; needing local records does not by itself require CLI.

## Bind the session and target

Read the browser-control documentation exposed in the current environment and use supported browser APIs. Reuse the existing official tab, account, remote instance, project and conversation where appropriate. Do not treat a documentation page, successful website login or familiar project names as proof of local execution. Record the execution environment and exact project root when exposed; otherwise preserve the uncertainty and use bounded input-access corroboration from the packet protocol. If the required browser target cannot be selected, keep the request unsent and choose the verified CLI target or ask for an explicit target change; do not silently substitute.

Check skills, plugins, tools and rules only as needed for the task. Record observed inventories separately for each route; do not infer automatic synchronization or full parity from sharing an account or machine. Preserve the client's normal harness and existing permissions. Relevant public search/page reading is allowed within consultation scope; interaction, publication and unrelated disclosure need their own authority.

## Send and continue

Prepare and scan the neutral packet using the skill's packet reference. Include request ID, target, exact input allowlist, permitted actions and named output paths where local writing is required. A consultation is not permission to edit the product or execute unrelated commands.

One controller owns UI mutations. Prefer current semantic controls, refresh affected state after changes, and verify project/model labels and composer content before sending. Persist UNKNOWN before Send, then SENT only after visible submission evidence. An ambiguous send, timeout or collection failure stays in the original conversation; never resend through CLI or another tab. Use the native workflow's bounded recovery principles for ineffective controls. Independent advisers may generate concurrently without holding UI ownership while waiting.

## Local records and controller capture

When useful, request named local output files for the original answer, a task log and an evidence index. The task log should identify actions, inputs, output paths, checks, actual errors and unresolved limits. Preserve existing files; create unique outputs unless an exact overwrite is authorized. Read back and hash the named files locally when accessible. Do not treat a promise to save, a displayed basename or a success summary as proof that a file exists on the intended machine.

Capture the complete original answer through supported UI text/export as well as available activity/tool results. Keep model-authored logs separate from controller observations; inspect actual tool errors even when the final answer says no failures. Record request/conversation locator, route, selected and observed model/effort/workflow, project/environment binding, input-access evidence, dispatch/collection state, output paths and material errors. A browser selection label is configuration evidence; absent effective runtime fields remain unverified. Never manufacture CLI stdout, exit codes, native metadata or model-authored completion records.

A bounded read of activity and the same conversation is enough for routine monitoring. Do not repeatedly reopen settings or click through every skill. If export or file writing fails, preserve the same original UI answer and report the collection limit; do not ask for a reconstructed answer. Apply the delivery reference to adviser-written files only when its exact schema was requested; a controller browser receipt is a separate record.
